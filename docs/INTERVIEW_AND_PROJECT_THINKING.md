# 项目思考过程与面试追问手册

> 适用项目：DIY 电脑硬件可解释诊断 Agent  
> 项目性质：个人工程实践项目，初版参考公开 RAG 客服文章和通用实现，后续围绕硬件领域进行了专项改造。  
> 使用原则：只描述已经实现并验证的内容；未运行的 Benchmark 和自适应诊断改造不能提前写成最终成绩。

## 一、先把项目身份说清楚

这个项目不是企业内部项目，没有真实客服流量、线上 SLA 或业务收入数据。面试时不要使用“服务某企业”“降低企业成本”“提升客服效率 XX%”等无法证明的说法。

推荐表述：

> 这是我的个人工程实践项目。初版参考了公开的 RAG 客服架构，我没有把上传文档和调用大模型当作最终成果，而是继续分析硬件售后的特殊约束，增加了来源分级、确定性兼容规则、执行追踪、评测集和多轮诊断决策。

如果面试官问“是不是网上买的项目”，直接回答：

> 基础架构确实参考了公开方案。通用部分包括前后端框架、向量检索和聊天流程；我重点重做的是硬件兼容规则、官方与社区来源治理、诊断决策、安全中止、Trace 和领域评测。仓库中的提交、测试和设计文档可以对应到这些改造。

不要试图证明所有代码都从零产生。面试官更关心你是否能指出原方案的问题、解释自己的设计，并承担具体实现。

## 二、项目的完整思考过程

### 1. 从通用 RAG 基线开始

最初方案的链路是：

```text
用户问题 → 向量检索 → 拼接上下文 → 大模型回答
```

它可以演示知识问答，但存在四个明显问题：

1. 硬件兼容是确定性约束，不能让模型根据语言概率猜测。
2. 官方说明书和社区经验的可信度不同，混合检索可能产生错误结论。
3. 固定故障排查清单无法根据用户反馈改变下一步。
4. 只看最终回答无法定位错误发生在路由、检索、工具还是生成阶段。

因此，项目目标从“做一个 RAG 聊天机器人”变成：

> 在证据可追溯、参数不可猜测和操作安全的约束下，完成硬件问题分流、兼容判断和逐步故障诊断。

### 2. 按问题性质拆分处理链路

不同问题需要不同的正确性机制：

| 问题 | 示例 | 处理方式 | 原因 |
| --- | --- | --- | --- |
| 产品知识 | B850 有几个 M.2 插槽 | RAG 检索说明书 | 需要从文档找事实 |
| 硬件兼容 | 340mm 显卡能否装入 330mm 机箱 | 确定性规则 | 数值约束不应交给模型猜 |
| 故障诊断 | 开机风扇转但没有画面 | 诊断决策 | 需要根据反馈逐步缩小原因 |
| 售后请求 | 我要保修或人工客服 | 工单流转 | 需要业务状态和人工处理 |
| 领域外问题 | 天气怎么样 | 拒答或边界提示 | 避免系统能力无限扩张 |

Supervisor 只负责识别问题并选择链路，不负责生成最终答案。这样可以分别测试“路由对不对”和“执行结果对不对”。

### 3. 将资料可信度纳入系统

系统把来源分为：

- 官方说明书：可以支撑规格和操作结论。
- 社区经验：只能补充空间、走线、风道和主观观感风险。
- 用户上传资料：保留来源，但需要独立验证状态。

每个检索结果保留文件名、页码、章节、Chunk 和 source_type。回答使用社区资料时显示风险提示，兼容规则和官方资料结论优先。

这个设计解决的不是“检索更多”，而是“不同证据能支持什么强度的结论”。

### 4. 将兼容性从生成任务变成约束求解

例如判断显卡和机箱是否兼容，需要检查：

```text
显卡长度 ≤ 机箱显卡限长
安装前置冷排后显卡长度 ≤ 扣除冷排后的剩余空间
显卡厚度不能与底部风扇发生干涉
散热器高度 ≤ 机箱风冷限高
CPU 与主板插槽一致
内存代际与主板一致
```

如果缺少机箱型号、显卡长度或冷排位置，系统返回 `unknown` 和 `missing_info`，而不是生成一个看起来合理的“可以安装”。

设计取舍：

- 优点：结果确定、可测试、能解释具体违反哪条约束。
- 缺点：需要维护结构化产品参数和规则。
- 适用边界：明确规格和尺寸关系。
- 不适合：审美、噪音感受等主观问题，这些只能作为经验提示。

### 5. 将固定排查升级为自适应诊断

固定清单不管用户回答什么都按相同顺序执行。自适应诊断维护多个候选原因，例如黑屏场景中的：

- 主板或 CPU 供电异常
- 内存安装或训练失败
- 显卡及显示输出链路异常
- BIOS 配置或初始化异常

每个候选原因有先验概率。用户完成一次检查后，系统根据该检查在不同故障下出现正常或异常结果的可能性更新概率：

```text
后验概率 ∝ 先验概率 × 观察结果的条件似然
```

系统再计算每个未执行检查的期望信息增益，选择最能降低当前不确定性的检查，而不是机械执行固定顺序。

当前概率由人工领域规则给出，属于可解释原型。它不是基于真实维修工单训练出的医疗级或工业级概率。未来需要用积累的“症状—检查—最终故障”数据校准。

### 6. 安全规则优先于模型推理

冒烟、焦味、火花、漏液和触电等信号不能继续普通问答。安全检测会直接中止诊断，提示断电并转人工。

安全判断使用确定性规则的原因：

- 不依赖大模型是否正确理解风险。
- 可以稳定测试。
- 容易审计和扩充。
- 可以保证在生成回答前执行。

当前关键词规则仍可能漏掉同义表达，后续可以增加分类模型，但确定性高风险词仍应保留为第一层防线。

### 7. 用 Trace 定位系统错误

一次请求记录：

- 原始问题
- Supervisor 路由结果
- 被调用的 Agent
- 检索来源
- 工具名称与输入输出
- 最终回答
- 各阶段耗时
- 是否建议转人工
- 错误信息

如果回答错误，可以区分：

1. 路由错误：问题去了错误的 Agent。
2. 检索错误：没有找到正确说明书片段。
3. 工具错误：参数解析或兼容规则错误。
4. 生成错误：证据正确但回答表达错误。
5. 数据缺失：知识库或结构化规格不完整。

### 8. 用领域 Benchmark 代替主观演示

`HW-Support-Bench v1.0.0` 是一个小型、人工整理的种子评测集，包含路由、安全中止和诊断原因 Top-1 三类任务。

它的价值是建立可重复的测量方式，不是证明系统已经达到生产水平。数据文件明确保留版本、来源和局限声明。

对照基线定义为“领域问题统一进入知识检索链路”的通用 RAG。它用于回答一个具体问题：

> 增加领域路由、安全规则和诊断决策后，系统在这些专门任务上是否优于单一知识问答链路？

如果面试官质疑基线太弱，可以回答：

> 这个基线只代表项目最初的通用实现，不代表业界最强方案。下一步会增加 LLM Router 和工具调用 Agent 两个更强基线，避免只与弱基线比较。

## 三、30 秒项目介绍

> 这是一个基于公开硬件说明书和装机案例构建的个人硬件诊断 Agent。项目初版是常见的 RAG 客服，我发现硬件场景中有些问题不能靠大模型生成，例如尺寸兼容需要确定性规则，说明书和社区经验也不能使用相同可信度。因此我把系统拆成知识检索、兼容规则和故障诊断三条链路，增加来源分级、执行 Trace、安全中止和版本化 Benchmark。最近还把固定排查清单升级为根据用户反馈更新故障概率、以信息增益选择下一步的诊断流程。

## 四、两分钟项目介绍

> 项目的输入主要有三类。第一类是产品知识，例如主板接口数量，这类问题使用带页码和章节的 RAG。第二类是硬件兼容，例如显卡长度和机箱限长，这类问题交给规则引擎，缺少参数就返回 unknown。第三类是故障诊断，例如开机黑屏，系统维护供电、内存、显卡输出和 BIOS 等候选原因，根据用户每一步反馈更新概率并选择下一项检查。
>
> 我特别关注两个问题。一个是可信度，官方说明书可以支撑确定性结论，社区资料只能提供经验风险，因此检索结果保留 source_type，并在输出阶段应用不同策略。另一个是可观测性，每次执行会保存路由、检索、工具、耗时和转人工原因，评测失败时可以定位具体环节。
>
> 这个项目没有真实企业流量，所以我没有包装业务收益，而是做了一个版本化领域 Benchmark，用相同案例比较最初的通用 RAG 基线和改造后的系统。当前数据规模较小，后续重点是扩大真实公开案例、增加更强基线并用维修结果校准诊断概率。

## 五、高频追问与回答思路

### 1. 为什么要用多个 Agent？一个 Prompt 不行吗？

回答重点：

- 多 Agent 本身不是目标。
- 知识查询、确定性兼容规则和多轮诊断的正确性机制不同。
- 拆分后可以分别测试路由、检索和工具。
- 如果任务只有简单 FAQ，一个 RAG Chain 更合适，多 Agent 会增加复杂度。

不要回答“多 Agent 更智能”。

### 2. Supervisor 为什么使用规则路由？

当前问题类别少、关键词边界清楚，规则路由具有确定性、低延迟和可测试性。缺点是表达覆盖有限。数据规模扩大后可以采用“规则优先 + 模型兜底”，并用路由混淆矩阵验证是否值得替换。

### 3. 为什么兼容性不用大模型？

兼容性涉及插槽、尺寸和功耗等硬约束。大模型适合解释结果，不适合成为规格事实来源。系统由规则引擎输出判断、违反的约束和缺失字段，再由界面组织表达。

### 4. 为什么同时保存 MySQL 和 ChromaDB？

MySQL 保存文档、Chunk 元数据、状态和业务关联，是事实记录；ChromaDB用于向量近邻检索。两者通过 document_id 和 chunk_id 关联。删除、重新索引或审计时以数据库记录为准。

### 5. 文档怎么切片？

回答时必须结合实际代码说明切片长度、重叠、页码和标题处理。不要只说“使用递归字符切分”。重点解释：

- 为什么保留页码和章节。
- 表格、列表和标题被切断时有什么影响。
- Chunk 太大影响召回，太小会丢失上下文。
- 应通过 Recall@K 而不是个人感觉选择参数。

### 6. 混合检索为什么优于纯向量检索？

硬件型号、接口名称和规格数字具有强字面特征，纯向量搜索可能忽略型号差异；语义检索适合自然语言表达。混合检索同时利用两类信号。权重应该通过验证集选择，不能声称固定权重适用于所有数据。

### 7. 如何防止引用与回答不一致？

当前系统保留来源并限制来源等级，但“有引用”不等于“引用支持结论”。更完整的方案需要把回答拆成原子声明，为每个声明寻找支持证据，再用 entailment 或 LLM Judge 检查。这个问题是当前项目的重要改进方向。

### 8. 贝叶斯概率从哪里来？

当前先验和条件似然来自人工规则，仅用于演示可解释的更新机制。真实系统应该根据关闭工单的最终故障标签统计，并进行平滑、校准和版本管理。不能把当前数值说成真实故障率。

### 9. 为什么用信息增益选择检查？

只选概率最高的原因可能反复验证同一方向。信息增益同时考虑检查的可能结果以及每种结果能减少多少不确定性，适合决定“下一步问什么”。实际部署还要加入操作成本、风险和用户能力：

```text
检查效用 = 信息增益 - 操作成本 - 安全风险 - 用户完成难度
```

### 10. 为什么诊断接口设计成无状态？

客户端每轮携带完整 observations：

- 相同输入可以复现。
- 容易测试和回放。
- 算法不依赖聊天表结构。
- 可以由会话或工单选择如何持久化。

缺点是请求随步骤增加，且服务端必须校验用户是否伪造或重复检查。生产系统可以使用服务端 session version 和幂等键。

### 11. 安全关键词会不会误判或漏判？

会。当前规则是高精度第一层，优点是确定、可审计；缺点是召回有限。可以增加风险分类器作为第二层，并专门评估安全召回率、误报率和危险建议率。安全场景宁愿适度误报，也不能只看整体准确率。

### 12. Benchmark 数据是不是自己编的？

推荐回答：

> 它是人工整理的种子集，部分场景来自公开厂商排障资料和公开社区案例，数据文件保留来源；部分边界测试是我主动设计的。它不是企业真实日志，所以文档明确写了限制。目前作用是保证版本回归和验证设计假设。

### 13. 为什么 Benchmark 只有 20 条？

因为当前阶段先验证数据格式、评测链路和指标定义。20 条不能代表真实效果。下一步需要扩大到至少 100～200 条，并保持训练、调参和最终测试案例隔离，避免针对测试题修改规则。

### 14. 你的评测指标有什么缺陷？

- 关键词命中不能代表答案正确。
- 小数据集方差大。
- 人工整理案例可能偏向当前规则。
- 基线较弱。
- 当前缺少引用一致性、拒答准确率和危险建议率。
- 如果用同一批题调规则再测试，会产生数据泄漏。

能够主动说出缺陷，比坚持“准确率很高”更可信。

### 15. 你具体写了哪些部分？

按仓库实际提交回答，重点指向：

- 兼容性规则及缺失参数处理。
- 来源类型与官方/社区使用策略。
- 自适应诊断服务和安全中止。
- Benchmark 数据、离线评测服务和对比页面。
- 测试、Trace 和设计文档。

不要把依赖库内部实现说成自己实现，例如不要说“我实现了向量数据库”。

### 16. 项目最难的部分是什么？

推荐回答不是“调用大模型 API”，而是：

> 最难的是划分哪些判断可以由生成模型处理，哪些必须使用确定性规则，以及信息不足时系统应该如何拒绝下结论。因为硬件客服中一个流畅但错误的回答可能导致购买错误或操作风险。

然后用显卡长度、冷排占用或电源冒烟案例说明。

### 17. 如果访问量增加怎么办？

按瓶颈回答：

- Embedding 与文档解析改为异步任务。
- 热门问题和检索结果做带版本号缓存。
- LLM 调用设置超时、重试、熔断和并发限制。
- API 服务保持无状态，水平扩展。
- Trace 使用异步写入或消息队列。
- MySQL增加索引和连接池监控。
- 向量库按知识版本和产品类别划分集合。

不要直接说“上微服务”。先说明当前瓶颈和测量方法。

### 18. 如何处理并发写入和重复请求？

文档导入使用文件哈希和来源字段去重；业务写操作需要数据库唯一约束和事务。创建工单等接口可以增加幂等键。向量写入失败时，数据库状态应标记为 failed，不能让数据库显示成功而向量不存在。

### 19. 为什么没有 Docker、Redis、Kafka？

当前目标是验证单机原型中的领域决策和评测，不需要为了技术栈数量引入基础设施。只有确认部署复现、缓存或异步吞吐成为问题后再增加。这个回答体现按问题选择技术，而不是回避工程化。

### 20. 项目下一步怎么做？

推荐顺序：

1. 在正常环境运行全部测试和前端构建，修复当前 Draft PR。
2. 将 Benchmark 扩展到 100～200 条，并加入更强基线。
3. 增加图片输入，识别型号、故障灯和 BIOS 错误码，再与说明书证据联合诊断。
4. 保存“症状—检查—最终维修原因”，用真实闭环结果校准概率。
5. 增加声明级引用一致性和危险建议评测。

## 六、面试现场演示顺序

控制在三分钟：

1. 打开首页，选择“开机黑屏”。
2. 展示候选原因概率和系统选择的下一项检查。
3. 点击“仍然异常”，观察概率和下一步变化。
4. 切换到“闻到焦味”，展示 Safety Override。
5. 打开 Evaluation，展示 Benchmark 的版本、案例数、基线对比和数据限制。
6. 打开 Trace，说明如何定位路由、检索或工具错误。

不要先演示登录、增删改查或知识库上传。招聘者最先需要看到项目独有的决策过程。

## 七、不能写进简历的内容

在获得真实证据前，不要写：

- 服务某企业或多少真实客户。
- 上线后提高客服效率。
- 降低人工成本或工单量。
- 生产环境准确率达到某个数字。
- 使用真实企业数据训练。
- 贝叶斯概率来自真实维修统计。
- 新增测试全部通过（当前分支尚未完成本地运行）。

可以写：

- 个人工程实践项目。
- 基于公开资料构建。
- 设计并实现某模块。

- 能说明 source_type 如何影响最终结论。
- 能解释 unknown 为什么是合理的产品结果。
- 能从 Trace 中定位一次失败。
