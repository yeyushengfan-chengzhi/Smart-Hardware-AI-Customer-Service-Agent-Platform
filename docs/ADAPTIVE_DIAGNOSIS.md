# 自适应故障诊断：从固定话术到可解释决策

## 为什么要做这项改造

常见 AI 客服项目会把用户问题交给大模型，再返回一组固定排查步骤。它无法利用用户刚完成的检查结果，也无法解释为什么下一步要做某项检查。本项目新增多轮诊断决策引擎：每轮根据历史观察更新故障原因概率，并选择预期信息增益最高的下一项检查。

## API

接口为 `POST /api/agent/diagnosis/next-check`。

首次请求：

```json
{
  "query": "主机开机黑屏",
  "fault_type": "no_display",
  "observations": []
}
```

用户完成检查后的下一轮请求：

```json
{
  "query": "主机开机黑屏",
  "fault_type": "no_display",
  "observations": [
    {"check_id": "debug_led", "outcome": "abnormal"},
    {"check_id": "memory_reseat", "outcome": "normal"}
  ]
}
```

`normal` 表示执行操作后问题消失或检查正常，`abnormal` 表示问题仍存在或发现异常，`unknown` 表示用户无法确认。服务端不保存会话状态，调用方每轮携带完整 observations，因此算法可以复现，也便于把诊断记录写入聊天会话或工单。

## 核心知识点

1. **贝叶斯更新**：用每个检查在不同故障原因下出现异常的似然，结合先验概率，计算观察结果后的后验概率。
2. **信息熵**：熵表示当前原因分布的不确定性。系统计算每项检查的期望熵下降，优先选择最能区分候选原因的检查。
3. **可解释决策**：响应给出原因排序、概率、所选检查的信息增益和选择说明，前端可以直接展示“为什么检查这一步”。
4. **无状态状态机**：状态由 query、fault_type 和 observations 完整表达，同一输入得到同一结果，便于测试、回放和审计。
5. **安全护栏**：冒烟、烧焦、火花、漏液、触电等关键词会中止普通诊断流程，要求立即断电并转人工。

## 面试时怎么讲

可以从具体例子开始：“黑屏不一定是显卡坏了。第一轮系统根据先验概率和各项检查的区分度选择诊断灯；用户反馈后，系统用似然更新内存、显卡、供电和 BIOS 四类原因的概率，再选择下一项信息增益最大的检查。”

工程取舍是：当前概率来自可审查的领域规则，适合数据量不足的原型阶段；积累真实维修工单后，可以统计检查结果与最终原因，校准先验概率和条件似然。算法保持确定性，因此比直接让大模型决定高风险硬件操作更容易测试和审计。
